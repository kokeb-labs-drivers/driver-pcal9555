Detailed Description

template<I2cPort Port>
class pcal9555::PCAL9555< Port >

Driver for one PCA9555 or PCAL9555A on a platform port.

Lifecycle: construct with the configuration (no I/O), EnsureInitialized() (bus up, presence check, every register written and read back), use, optionally Deinitialize() (every pin back to an input). Every call that touches the chip returns Error::NotInitialized until EnsureInitialized() has succeeded; no call starts the chip implicitly.

Pins are numbered 0 to 15: 0 to 7 are P0_0 to P0_7, 8 to 15 are P1_0 to P1_7. Calls that change pins take a mask (bit n = pin n, PinMask() builds one); a mask of 0 is InvalidArgument. The driver keeps a copy of every register it wrote (GetConfig()): a pin call computes the new register pair from that copy and writes it in one transfer, without reading it first. Nothing is read back unless the call's last argument is Verify::ReadBack (Verify::None by default); only then can a pin call return WriteMismatch.

Every call listed below as returning Bus returns NoDevice instead when the port's optional GetLastFailure() hook reports that nothing acknowledged the address (the chip was removed or lost power). The chip NACKs no transfer the driver sends by design (handbook KB-CPP-130).

Neither part has a reset pin or a reset flag, but a supply dip below the power-on reset voltage reloads every register with its power-up value (section 6.4, table 4). The driver finds that by reading one register whose copy differs from its power-up value (detail::FindResetSentinel()): in CheckForReset(), SetDirection(), ApplyConfig(), and in a setter about to rewrite that register (so a setter returns DeviceReset only when it would have rewritten the evidence; the others send their one write as before). A call that finds it writes nothing, marks the driver uninitialised and returns DeviceReset; EnsureInitialized() then writes the copy again in the datasheet's order.

A write whose transfer failed with Bus may still have reached the chip (a NACK or an ACK lost after the bytes were clocked in). The copy then takes the riskier of the old and the asked value (detail::Riskier(): an output rather than an input, the written level, the stronger drive, push-pull) and the register is unknown: the next call that builds on it reads it into the copy first (one more read), a successful write or a read-back call makes it known again, and the reset check never reads it. NoDevice, an address NACK, proves nothing arrived: the copy stays.

The Agile I/O calls (drive strength, pull resistors, input latch, interrupt mask and status, output mode) need Config::variant == Variant::Pcal9555a; on a driver configured for the PCA9555 they return Unsupported without I/O.

Optional port hooks, found at compile time:

Hook Used for Without it
void Log(LogLevel, const char* message) noexcept One line per lifecycle event or failure Nothing is logged
bool GetLastFailure(I2cFailure& failure) noexcept Telling an address NACK (NoDevice) from other bus failures Every failed transfer is Bus

A hook declared with the wrong signature (for example void GetLastFailure(...)) is a compile error. The chip needs no wait between transfers, so the port has no DelayUs() hook, and it has no reset pin, so there is no GpioSet() hook.

◆ CheckForReset()

template<I2cPort Port>
Result< void > pcal9555::PCAL9555< Port >::CheckForReset ( )
noexcept

Find out whether the chip went through a power-on reset since the start.

Neither part has a reset flag (section 6.4). The driver reads one register whose copy differs from its power-up value (table 4), preferring the Agile I/O pairs and the polarity pair, then 0x4F, the configuration pair and the output pair (detail::FindResetSentinel()); if it reads its power-up value, the chip reset. When every register of the copy is at its power-up value nothing is sent: a reset then leaves the chip as the driver believes it to be. Call it where a supply dip is possible, for example once per control period or before a critical output change: one 2-byte read (one 1-byte read when 0x4F is the register), 113 µs at 400 kHz. A register whose last write failed is never the one read; when no other is left, the check reads the unknown ones instead (one read each), and one back at its power-up value is a reset. When the failed write's old or new value was itself the power-up value, that is a false DeviceReset: one time, recovered by EnsureInitialized().

A write to that register that the chip acknowledged but dropped reads the same way; the recovery is the same. SetDirection(), ApplyConfig() and a setter about to rewrite the checked register run the same check first.

Returns
Ok, NotInitialized, Bus or DeviceReset (the driver is now uninitialised: call EnsureInitialized(), which writes every register again in the datasheet's order).

◆ EnsureInitialized()

template<I2cPort Port>
Result< void > pcal9555::PCAL9555< Port >::EnsureInitialized ( )
noexcept

Start the chip on the first call; Ok at once, with no I/O, once it has succeeded.

Checks the stored configuration with Validate() and the address, brings the bus up, checks that the part answers, writes every register of the configuration and reads each back. The chip has no reset pin and no software reset, so instead of a reset every register the driver owns is written, which also undoes whatever a previous run left behind. The presence check reads the input ports, which also clears an interrupt left pending from before the start (an address NACK is NoDevice with a port that has GetLastFailure(), otherwise Bus); on a PCAL9555A it also reads the output port configuration register, whose reserved bits 7..2 read 0. The identity check then writes reg::kIdentityPattern to the polarity inversion pair and reads it back, which no floating, stuck or deaf line can echo, before any configured value is written; the read-back of every register after the writes confirms it: a register that does not hold what was written means another part answers. After a failure the driver stays uninitialised and the next call starts again from the beginning.

Returns
Ok, InvalidArgument (the configuration or the address; no I/O), Unsupported (an Agile I/O field for a PCA9555; no I/O), NoDevice, Bus or DeviceIdMismatch.

The configuration stored or last applied, updated by every successful pin call: the driver's copy of the chip's registers. No I/O.

After a write that failed with Bus the register is unknown: the chip may hold the old value, the written one or (a pair) one byte of each. The copy then shows the riskier of old and written for the direction (an output), the drive strength (the stronger) and 0x4F (push-pull), and the written value for every other field, the output levels included: not necessarily what the pins do. The driver reads an unknown register from the chip before it builds on it; to see the chip now, call ReadOutputLatch(), ReadInputMask() or ReadPolarityInversion(), which also make the register known again.

Read one register, once: one 1-byte write-read, no retry, no check of the value (handbook KB-CPP-129). For bring-up and diagnostics.

Side effects are the chip's own: reading an input port (0x00, 0x01) clears that port's interrupt (section 6.5), without the status read ReadInputs() does first. The value also updates GetLastInputs(), GetLastOutput() or the interrupt latch, as the same register read by any other call would.

Set the direction of the pins in mask (configuration registers).

To avoid a glitch, set the output level with SetOutputs() before making a pin an output.

A pin that becomes an output drives its output latch through its port's output stage at once, and a power-on reset sets the latch high and the stage push-pull (table 4). So the call first checks for a reset (CheckForReset(), one read) and then writes, from the driver's copy, in the datasheet's order (section 6.2.12): 0x4F (PCAL9555A), the output pair, the configuration pair. When pins become outputs, even a reset that the check missed makes no pin an output at the reset latch level or stage. The one exception is a partial release (below): a reset in the microseconds between its check and its configuration write leaves the pins that stay outputs at the power-up level until the 0x4F and output writes after it land. Cost: one read and two write pairs on a PCA9555, one read, one 1-byte write and two write pairs on a PCAL9555A (no read when the copy is all power-up values).

Releasing pins (Direction::Input) is the safe direction. When every pin ends up an input, the configuration pair is the only transfer, with no check: nothing can be driven. When other pins stay outputs: the check, then the configuration pair first (the pins are released by the first write), then 0x4F and the output pair for the remaining outputs.

Parameters
maskPins to change; not 0.
directionThe direction.
verifyVerify::ReadBack to read the configuration pair back (one more read); a value that is not an enumerator is InvalidArgument.
Returns
Ok, NotInitialized, InvalidArgument, Bus, DeviceReset (nothing written) or WriteMismatch.
