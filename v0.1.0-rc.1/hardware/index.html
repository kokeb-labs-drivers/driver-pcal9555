Source of this table and of the chip figures: docs/hardware.yml.

At power-up every I/O is an input with a weak (about 100 kΩ) pull-up to VDD, so unused pins do not float. On the PCA9555 the pull-up is fixed (PCA9555 section 6.4); on the PCAL9555A it can be switched to a pull-down or off per pin (Agile I/O). Neither part has a reset pin: the only reset is the power-on reset, so the port has no GPIO hook. The pinout, the block diagram, the circuit and both tables are drawn from docs/hardware.yml.

Typical application¶

Figure 13 of the data sheet, reduced to the bus, the interrupt and one output: 10 kΩ pull-ups on SCL, SDA and INT, the address pins tied to VSS (address 0x20), and an LED with a 2 kΩ series resistor sunk by P0_0. The MCU and the expander share the 3.3 V supply, which sets the I2C logic levels (Power).

Address¶

7-bit address 0100 A2 A1 A0 (section 6.1): 0x20 to 0x27, eight chips per bus. AddressFromPins(a2, a1, a0) computes it; kI2cAddress (and its older name kDefaultI2cAddress) is 0x20. EnsureInitialized() rejects any other address with InvalidArgument before it touches the bus.

Registers¶

Table 4. The PCA9555 has the first eight registers; the PCAL9555A adds the Agile I/O bank. Pin n of the driver is bit n of a 16-bit pair: port 0 in the even register (bits 7..0), port 1 in the odd one.

Figure description and sources

One card per register pair, in command-byte order; port 0 is the even byte, port 1 the odd one. The top band is the standard bank, 0x00 to 0x07, on both the PCA9555 and the PCAL9555A; the lower band is the Agile I/O bank, 0x40 to 0x4F, which only the PCAL9555A has. Each card gives the access (R or R/W), the power-up value of each register, the Config field the driver keeps for it, and the calls that read or write it. EnsureInitialized() and ApplyConfig() write every Config field shown. The input ports and the interrupt status are read only, so they have no Config field. Addresses come from the constants in inc/pcal9555_registers.hpp, fields from the pair lists in inc/pcal9555.hpp and calls from src/pcal9555.ipp.

Reading an output port register returns the output latch, not the pin. The input port registers reflect the pin whether it is an input or an output. inc/pcal9555_registers.hpp has the map as the driver uses it.

Bus transactions¶

Section 7. After the address byte the master sends a command byte, which sets the pointer. Each data byte then goes to (or comes from) the pointed register, and the pointer moves to the other register of the pair: a write of two bytes after command 0x02 sets output port 0, then output port 1. The pointer never moves on to the next pair, so the driver moves at most one pair per transfer.

With Verify::ReadBack (the last argument of a setter; Verify::None by default), add one read pair (113 µs) after each write pair and one read (90 µs) after the write of SetOutputMode() (SetDirection(): one read pair after the configuration pair). The times are derived (9 clocks per byte), not measured, and leave out START, STOP and your port's overhead.

Unimplemented command bytes¶

Neither data sheet says how a part answers a command byte it does not implement, such as 0x4F on a PCA9555. The driver assumes a NACK and therefore never auto-detects the part: Config::variant names it. Configured as a PCAL9555A on a PCA9555 that NACKs, EnsureInitialized() fails with Bus at the 0x4F read, before any write. If a part instead used only the low three bits of the command, 0x4F would read configuration port 1, which is 0xFF after power-up; the reserved-bits check then fails with DeviceIdMismatch, still before any write. Not verified on hardware: bench step 4 in Troubleshooting checks it.

Timing¶

Neither part needs a wait between transfers: there is no conversion, no reset sequence and no programming time, so the driver never waits and the port has no DelayUs() hook.

f_SCL I2C clock 0 to 400 kHz 0 to 400 kHz
t_v(Q) SCL to output valid, after the data byte's ACK 400 ns max 200 ns max
t_v(INT) Input change to INT valid 1 µs max 4 µs max
t_rst(INT) SCL (ACK of the input read) to INT released 1 µs max 4 µs max

Interrupt¶

Section 6.5. An input that changes raises INT; reading the input port of that pin releases it, as does the pin returning to its old level before the read. A pin configured as an output never raises INT, and turning an output into an input can raise a false interrupt when its level differs from the input register.

PCA9555 PCAL9555A
Which pins raise INT Every input, always Inputs whose interrupt mask bit is 0; all masked at power-up
Which pin raised it Compare ReadInputs() with the last value ReadInterruptStatus() (masked pins read 0); the status does not clear INT
Short pulses Lost if the pin returns before the read Kept with the input latch: the input register holds the level that raised INT until it is read

Reading one port (ReadPin()) releases only that port's interrupt; ReadInputs() reads both. The read also clears the interrupt status bits of the port (section 6.2.11), so on a PCAL9555A with an unmasked input the driver reads the status pair into GetLatchedInterrupts() first. INT is open-drain, active low: pull it up to the MCU's VDD and wire it to an MCU input. The driver never runs in the ISR: signal a task, which then calls the driver (API guide).

Power¶

Parameter PCAL9555A PCA9555
Supply 1.65 V to 5.5 V 2.3 V to 5.5 V
I/O 5.5 V tolerant 5.5 V tolerant
Output sink current per pin 25 mA (drive strength 11b) 8 mA min at V_OL = 0.5 V
Total ground current 200 mA (limiting value) 200 mA (limiting value)
Total supply current (sourced by the I/Os) 160 mA (limiting value) 160 mA
  • The supply sets the I2C logic levels: run the expander from the MCU's I/O voltage, or level-shift SDA and SCL.
  • Power-on reset: every register returns to its power-up value when VDD rises from below the power-on reset voltage (section 6.4 and 8.3, which also give the required ramp and the glitch limits). After a brown-out the registers are back at their defaults while the driver still holds its copy: outputs high, push-pull, every pin an input. CheckForReset(), SetDirection() and ApplyConfig() find that and return DeviceReset, and SetDirection() writes 0x4F and the output pair before the directions, so a reset never turns the old outputs back on high: see API guide.
  • Leakage: a pull-up or pull-down that fights an external level draws current; disconnect unused resistors with SetPull(mask, Pull::None).
